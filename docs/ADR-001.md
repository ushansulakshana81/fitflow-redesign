# ADR-001: Adopt a service-oriented architecture with a dedicated AI microservice

- **Status:** Accepted
- **Date:** 2026-09-20
- **Deciders:** FitFlow engineering team
- **Supersedes:** n/a (first ADR for the redesign)

## Context

The legacy FitFlow application was a single monolithic backend coupled to a single client.
This made it difficult to:

1. Scale AI-heavy features (recommendations, computer vision) independently of social and
   workout traffic.
2. Use the best tooling for each domain — the ML team needed Python, while the app team
   worked in TypeScript.
3. Deploy safely; any change required redeploying the entire system and risked a full outage.

The team decided to redesign FitFlow as a modular, service-oriented system.

## Decision

We will decompose FitFlow into the following top-level components:

- **`frontend/`** — a React Native (Expo) app targeting iOS, Android, and web.
- **`backend/`** — Node.js + NestJS services split by bounded context:
  - `auth` — identity, sessions, OAuth2/OIDC
  - `workout` — exercise plans, logging, progress
  - `nutrition` — meal tracking, macros, diet plans
  - `social` — feeds, follows, activity sharing
- **`ai-service/`** — a Python + FastAPI microservice containing:
  - a recommendation engine (personalized workout/nutrition suggestions)
  - a computer vision pipeline (pose estimation and form analysis)

Services communicate synchronously over REST (public) and asynchronously over a RabbitMQ
message bus for events such as workout completion and social activity, which feed the
recommendation engine.

## Consequences

### Positive

- Independent scaling of high-load and AI-heavy paths.
- Polyglot fit: TypeScript for the app/API, Python for ML/CV.
- Isolated failure domains and safer, service-scoped deployments.
- Clear ownership boundaries mapped to business capabilities.

### Negative / trade-offs

- Increased operational complexity (orchestration, monitoring, tracing).
- Distributed data requires eventual consistency in some flows.
- Cross-service contract management and testing overhead.

### Mitigations

- Adopt OpenTelemetry for unified tracing/metrics.
- Publish OpenAPI contracts per service and run contract tests in CI.
- Use RabbitMQ for reliable, decoupled event delivery.
